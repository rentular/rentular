# Quick Task 261114-e2e: Browser tests that type into every form field, a local test account, and a testing guide for the operations manager

## Why

A user (Jeroen) reported that in the onboarding "add a tenant" step every typed letter moved focus away (to the Next button), so he had to click back into "First name" after each letter. Cause: `FormField` was declared inside `OnboardingPage` (apps/web/app/onboarding/page.tsx), so every render created a new component type and React remounted the input. Fixed in 0eae15c and deployed, but never verified by typing. The owner wants it verified in a real browser, all other fields checked for the same problem, a test account, and instructions for the operations manager for continuous testing.

## Constraints that shape the design

- Claude never enters passwords or test credentials on production (rentular.com). All automated browser testing runs against a LOCAL stack (localhost). Test credentials are generated and recorded only in a local, gitignored env file plus a committed example file with placeholders.
- Tools available offline on this Mac: Docker 29 with image mariadb:11 cached; Playwright 1.58.2 in node_modules (playwright-core) with Chromium and WebKit browsers in ~/Library/Caches/ms-playwright. redis:7-alpine and mailpit images may need a pull: try `docker pull`; if the network is unavailable, check whether the API can boot without Redis (BullMQ) or whether a local redis-server binary exists (brew), and document the fallback. Do not add new npm dependencies unless already in the lockfile/store (`pnpm install --offline` to check); if @playwright/test is not available, write the runner on playwright-core with a small assertion helper.

## Task 1: Local e2e stack and seeded test account

- `e2e/` at the repo root (or `apps/web/e2e`, follow the repo layout): a script `e2e/run-local.sh` that starts MariaDB (+ Redis, Mailpit if possible) via docker-compose.yml on non-conflicting ports, creates the schema with `pnpm db:push` (never db:generate), starts the API and web (dev or production build, whichever is reliable) against it, waits for health, runs the tests, and tears down. Idempotent; leaves nothing running.
- Seed script `e2e/seed.ts`: creates two users directly in the local DB through the same password hashing the app uses (bcrypt): (a) `onboarding@e2e.local`, onboarding not complete, no data; (b) `landlord@e2e.local`, onboarding complete, with 1 property, 1 tenant, 1 lease, a few payments. Generate a random password at seed time, write it to `e2e/.env.e2e.local` (gitignored) and keep `e2e/.env.e2e.example` with placeholders. Never print the password in logs.
- Login in tests through the real login page (localhost only).

## Task 2: Focus-retention sweep (the bug class)

- A reusable helper `typeAndAssertFocus(page, locator, text)`: clicks the field, types the text one character at a time with a small delay (`pressSequentially`), and after EVERY character asserts that `document.activeElement` is still the same element (compare a data attribute or the element handle) and that the value equals the prefix typed so far. Report the page, field label and the character index where focus was lost.
- Generic sweep: for every page/dialog with inputs, find all visible `input` (text, email, tel, number, date where typing applies, search), `textarea` and contenteditable fields, and run the helper with a realistic string (e.g. "Jansens-Dupont 12" for text, an email for email, digits for tel/number). Skip read-only/disabled/file inputs. Cover at least:
  - onboarding: every step (property, tenant, lease, payment) for user (a);
  - register and login pages, invite accept page if reachable;
  - properties: create and edit dialogs; tenants: add and edit dialogs (including the "add" flow with a Next button if any); leases: create/edit contract form including indexation setup and the new "Lease registered" toggle area, reminder mute dialog; payments page dialogs (record payment, cost, rent-free, deduction, ignore reason); communications: custom message composer; settings pages (profile, SMTP, notification settings, bank connections including the Enable Banking wizard inputs: application id field); overview search/filter inputs; any search box in tables.
  - Run the sweep in Chromium and in WebKit (Safari engine) with a mobile viewport (iPhone 13 size) as well as desktop.
- If the sweep finds other fields with the same problem, fix them in this task (same cause: components declared inside components, keys that change on every render, state updates that re-create the field, autofocus effects) with one commit per fix, and re-run.
- A regression test that reproduces the original bug: run the onboarding tenant step test against the parent of 0eae15c in a scratch worktree if practical (optional, document either way); at minimum assert it passes now.

## Task 3: Smoke flows

- A small set of happy-path flows on the local stack: complete onboarding; add a tenant; create a contract; record a payment; mute reminders until next week and unmute; open the contract communication page; switch language NL/FR/DE/EN and check no raw translation keys (`/[a-z]+\.[a-zA-Z]+\.[a-zA-Z]+/` shaped strings) and no "Rentulair" in the DOM; check `<html lang>` follows Accept-Language when no cookie is set.

## Task 4: Guide for the operations manager

- `docs/TESTING-OPERATIONS.md` (plain English, practical, no dashes, human tone), for a non-developer operations manager:
  1. Automated: how to run `e2e/run-local.sh` (prerequisites: Docker Desktop, Node 20.19 + pnpm 9.15 via the repo's pins), what green/red output means, where screenshots/traces of failures land, how to send them to the developer.
  2. When to run: before every deploy, and weekly; also after any change to forms.
  3. Manual checks on production with their OWN dedicated test account they create themselves on rentular.com (suggested address pattern, e.g. ops-test+rentular@<their domain>; use a password manager; never reuse a real password; keep the account to fake data: one fake property "Teststraat 1, 1000 Brussel", one fake tenant with their own email so reminders go to them, never a real tenant). A short weekly checklist: log in on desktop and on an iPhone and an Android phone; add/edit a tenant (type a long name, watch the cursor stays), create a contract, open the communication page, check the language follows the phone, check the Android app opens and the version check passes, check a reminder email arrives in their mailbox when they trigger a manual reminder to their fake tenant, check the Enable Banking guide page loads. How to report a bug (screenshot, phone model, browser, steps, time).
  4. What not to do on production: no real tenant data in the test account, never mark payments on real contracts, never change bank connections of real landlords.
- Link the guide from README.md and CONTRIBUTING.md.

- No em-dashes or en-dashes; no Co-Authored-By lines. Never deploy, never touch prod, never enter credentials on any non-local host, never run db:generate.
