# Phase 11.2 Plan 02: Address data and the formal_notice type Summary

**Nullable postal address on users and correspondence address on tenants, formal_notice appended last to communications.type, the production DDL hand-written as packages/db/sql/formal-notice.sql with a drift guard, and both addresses writable through the settings and tenants routes with bounded input.**

## Accomplishments

- The letter's sender block has a data source: six nullable address columns on `users`, `country` defaulting to `BE`.
- The addressee block has an override: six nullable `correspondence_*` columns on `tenants`. `correspondence_country` deliberately has no default, so "no correspondence address on file" is distinguishable from "lives in Belgium".
- `communications.type` accepts `formal_notice` as its 16th and last value, in the Drizzle array and in the `CommunicationType` union. The other 15 values keep their existing order and ordinals.
- `packages/db/sql/formal-notice.sql` carries the three additive statements the operator applies on m1 in plan 11.2-09, with a header explaining the backup, the idempotency and why the file is hand-written.
- A unit test pins the SQL file to the schema: the quoted ENUM list must equal `communications.type.enumValues` element by element, every column add must be `ADD COLUMN IF NOT EXISTS`, and the file must contain no DROP, TRUNCATE, DELETE or RENAME.
- Both addresses are writable and readable through the existing API routes, bounded to the column widths.

## Decisions Made

- The guard test reads the SQL file through a path resolved from `import.meta.url` and strips comment lines first, so prose in the header cannot satisfy the additive-only assertions.
- `normalizeCorrespondence()` is a small named helper in `tenants.ts` rather than inline ternaries at six call sites, because POST and PATCH both need the same trim/null/upper-case rule.
- `GET /settings/profile` falls back to `"BE"` for a null country and `""` for the rest, matching how the existing `vatNumber` and `whatsappNumber` fields behave on that endpoint (flat body, no `{ data }` envelope).

## Assumption Drift (advisory)

**1. The settings test harness**
- **Planned:** `settings.test.ts` has an existing harness the four new behaviors can be hung off ("extend settings.test.ts with the four settings behaviors using its existing harness").
- **Actual:** It had no route harness; one had to be written, including a working `getDb()` mock.
- **Why:** The file predates the route-test pattern that `manualMarks.test.ts` established, and only ever tested exported constants.
- **Cost if wrong:** None to the product. The reading risk is that a future planner again assumes `settings.test.ts` can mount a router for free; it can now, which is why this is recorded.

Nothing else drifted. The enum order, the column shapes and the DDL idiom were exactly as the plan and research described, including the 15-value starting list.

## Issues Encountered

- The chain-proxy db mock resolves on any `await`, including `await db.update(...)`, which would have eaten queued select rows in the PATCH test. The proxy is parameterised by statement kind and only dequeues for selects, so the PATCH queue stays readable as the five selects the handler actually makes.
