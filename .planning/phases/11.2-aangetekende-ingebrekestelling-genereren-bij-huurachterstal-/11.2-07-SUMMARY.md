## Decisions Made

- **Locale edits by script, not by hand.** All four files round-trip byte-identically through `JSON.stringify(JSON.parse(raw), null, 2) + "\n"`, verified before any write, so a script that parses, inserts at a named anchor and re-serialises produces a purely additive diff (84 added lines per file, 2 reflowed lines where a trailing comma appeared). Hand-editing 4 x 60 lines at four different anchors invites a missed comma or a key in the wrong object.
- **Accents and umlauts spelled correctly** (`Numéro`, `Boîte`, `Straße`, `ausfüllen`), which is the dominant style in the fr and de files (509 and 372 lines carry accented characters). The older properties address block has unaccented variants (`Numero`, `Strasse`); I did not touch it, so the two label sets differ by accent only.
- **`channelBadge()` falls back to the letter styling with the raw channel name**, as the plan specified, rather than to SMS. The bug being fixed here is exactly a wrong-label fallback, so the new fallback is honest about not knowing.
- **`Communication.channel` widened to `string`.** The interface claimed `"email" | "sms"`, which was already a lie for whatsapp and signal rows and would have made the badge lookup dead code under `tsc`.

## Assumption Drift (advisory)

**1. The channel ternary was not only mislabelling SMS, the type behind it was wrong too**
- **Planned:** replace a two-branch ternary with a lookup, a pure rendering change.
- **Actual:** the lookup could not compile against the declared `channel` union, so the interface had to be corrected as well.
- **Why:** the page's `Communication` interface predates the whatsapp, signal, letter and internal channels and was never widened when the API gained them.
- **Cost if wrong:** Nothing ships differently. The record is here because a reader might assume this plan only touched presentation in that file.

**2. `BelgianCityInput` cannot carry a maxLength for the city field**
- **Planned:** `maxLength` on every input equal to the server bound (threat T-11.2-34).
- **Actual:** the street, number and box inputs got `maxLength` (255, 20, 20). The shared `BelgianCityInput` hardcodes `maxLength={4}` on the postal code (within the server's 10) and sets no limit on the city, and it is not in this plan's `files_modified`.
- **Why:** adding a prop to a component used by the properties form would have widened the plan's blast radius for a client-side convenience. The server-side Zod bound from plan 11.2-02 is the enforcing control for city (400 on over-255, with a test), exactly as the register says.
- **Cost if wrong:** a landlord can type a 300-character city and get a 400 instead of being stopped at 255. Annoying, not unsafe. Fixable later by giving `BelgianCityInput` a `cityMaxLength` prop.
