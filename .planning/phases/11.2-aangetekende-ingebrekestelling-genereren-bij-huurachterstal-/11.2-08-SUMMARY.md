# Phase 11.2 Plan 08: The contract page controls Summary

**The contract detail page now carries a Formal notice card next to the reminder actions: a dialog takes a payment deadline (16 days, with the calendar date shown before generating) and an optional paragraph, downloads one PDF per liable tenant by decoding the API's base64 client-side, shows what the letter claims, and letter rows in the history can be marked as posted with a date and the bpost barcode.**

## Accomplishments

- `FormalNoticeCard` sits directly under `ReminderMuteCard` inside the same `data &&` guard, so the generate control is where the landlord already handles late rent, with the property and tenant name passed as the dialog's label.
- The deadline field starts at 16 and the dialog shows `deadlineDate` with the resolved calendar day through `formatDate(addDaysYmd(todayInZone(), n))`, so the landlord reads 05/12/2026 and not a day count. An out-of-range or non-integer value replaces that line with `errors.invalid_deadline` in red and disables Generate, mirroring the server's `z.number().int().min(1).max(90)`.
- **The PDF is decoded, not streamed.** The response is JSON with `pdfBase64`, which is exactly the trap this plan could have fallen into. `downloadPdf()` runs `atob`, fills a `Uint8Array` byte by byte, wraps it in a `Blob` of type `application/pdf`, hands the object URL to a synthetic anchor with `download = filename`, clicks it, removes the anchor and revokes the URL in a 1000 ms timeout. `URL.revokeObjectURL` is unconditional; without it the bytes live for the rest of the browser session.
- Every letter in `data.letters` is downloaded in order, so a contract with two liable tenants saves two files, and each is listed by `letterFor` with its own Download again button that re-runs the helper from the bytes already in state.
- A letter whose `communicationId` came back `null` shows `notLogged` in amber under its row, because the landlord then holds the only copy.
- The claimed amounts are the API's: `rentOwed`, `interest` and `fee` only when above zero, `totalClaimed` in bold and the deadline as a date. No arithmetic runs on the client.
- `missing_sender_address` renders its sentence plus a `next/link` to `/settings`, which is the form plan 07 built, so the dead end has an exit.
- In the history, a row with `channel === "letter"` and `type === "formal_notice"` reads `posted.notPosted` in its status pill while queued, gains a Mark as posted / Change posting date button beside the show-body toggle, and once recorded prints `posted.summary` or `posted.summaryWithReference` under the recipient line. Every other row is byte-identical to before.
- One `MarkPostedDialog` is mounted at page level and driven by a nullable `postedTarget`, so a history of 100 rows does not mount 100 dialogs.

## Decisions Made

- **The client never computes an amount.** `rentOwed`, `interest`, `fee` and `totalClaimed` are rendered straight from `totals`. `tableSum` and `adjustment` come back in the payload and are deliberately not shown: they exist so the API can explain a difference between the month table and the authoritative debt, and surfacing them next to the total would raise a question the dialog cannot answer. If a landlord disputes a figure, the letter and the screen say the same thing because they share one source.
- **The result view replaces the form, and closing clears it.** `result` holds every PDF's base64, so leaving it mounted would keep the bytes of several tenants' letters alive behind a closed dialog. The reset effect nulls it on both open and close (T-11.2-40).
- **`not_markable` got a sentence instead of a fallback.** See the deviation below. The fallback would have told the landlord "the posting date could not be saved" when the real reason is that the row is a failed or cancelled letter, which is a different action on their part.
- **The mark-as-posted button is a text button next to the show-body toggle,** not a third element in the status area, so the row's shape does not change for the other 99 percent of history items.
- **`item.id` is the communication id.** The history endpoint returns the communications row id as `id`, which is what `/:id/posted` takes, so no extra field was needed.
- **The posting dialog does not pre-validate the date window.** The server owns the plausibility window (not after today in the schedule timezone, not before the row's creation day) and it is the only side that knows the row's creation day. The client only refuses an empty value and shows the server's `invalid_posted_date` sentence.

## Known Stubs

**The blob download will not save a file in the Android WebView app.** This is the one place where the shipped behaviour is known to be incomplete, and the project's rule is to say so rather than ship it quietly.

- `android-app/app/src/main/java/com/rentular/app/MainActivity.kt:195` sets a `DownloadListener` that builds `DownloadManager.Request(Uri.parse(url))`. `DownloadManager` accepts `http` and `https` only; a `blob:` URI is rejected. On most WebView builds the listener is not even invoked for a programmatic `a[download]` click on a blob URL, so the tap produces nothing at all: no file, no error, no notification.
- Nothing in this plan's file scope can fix that. The fix belongs in the wrapper (a `@JavascriptInterface` that takes the base64 and writes it with `MediaStore`, or a JS shim that posts the bytes to the native side), or in the web app by sending the landlord to a real `https` URL for the PDF instead of a blob. Either is a change outside `files_modified` and outside this plan's objective.
- In a desktop or mobile **browser** (Chrome, Firefox, Safari) the anchor-plus-blob download is the standard pattern and is expected to work; that still has to be confirmed by hand in plan 11.2-09, since no browser ran here.
- Suggested follow-up for the phase's remaining work or the backlog: decide between a native download bridge and an `https` PDF endpoint, then verify on the phone. Until then, the documented path for a phone user is to generate the letter from a browser.

No other stubs. Both dialogs are wired to live endpoints, every string resolves from a locale file, and the history reads the proof the API stores.
