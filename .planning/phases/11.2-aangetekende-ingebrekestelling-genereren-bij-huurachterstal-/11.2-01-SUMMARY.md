# Phase 11.2 Plan 01: pdfkit and letter fonts Summary

pdfkit 0.20.2 is installed in apps/api behind a human-approved supply-chain gate, with Liberation Sans Regular and Bold plus their SIL OFL licence committed as repo assets, so the letter renderer can embed names outside Latin-1 without touching Chromium or system fonts.

## What Was Built

**Task 1 (checkpoint, blocking human gate).** No repo changes. Both packages were tagged `[ASSUMED]` in research because slopcheck could not run (no pip/pipx/uv on the box), so the executor printed the exact install targets, the two registry links and the manual checks research had recorded, then stopped. A read-only `npm view` re-check was included as supporting evidence: pdfkit 0.20.2, MIT, repo `git+https://github.com/foliojs/pdfkit.git`, maintainers devongovett / diegomura / blikblum / liborm85, and no `postinstall`, `preinstall` or `install` hook among its scripts; `@types/pdfkit` 0.17.7 with `scripts = {}` from DefinitelyTyped. The user answered "approved". Nothing was installed before that answer: the tree was clean and the lockfile untouched at the point of the pause.

**Task 2 (install and fonts).** Re-ran `npm view pdfkit@0.20.2 scripts` before installing and confirmed no install-time hook. Then:

- `pnpm --filter @rentular/api add pdfkit@^0.20.2` and `pnpm --filter @rentular/api add -D @types/pdfkit@^0.17.7`.
- `apps/api/assets/fonts/` created with both TTFs copied from `/usr/share/fonts/truetype/liberation/` (410,820 and 414,568 bytes, both verified byte-identical to the system originals with `cmp`), plus `LICENSE-Liberation.txt` carrying the Red Hat and Google copyright lines and the full SIL Open Font License 1.1 text.
- `git check-ignore` on the font path exited 1 as research predicted, so no `.gitignore` change was needed, and the three files were staged explicitly.

## Deviations from Plan

### 1. [User requirement at the checkpoint] Caret ranges instead of exact pins

- **Found during:** Task 1 approval message.
- **Planned:** `pnpm --filter @rentular/api add pdfkit@0.20.2` and `@types/pdfkit@0.17.7`, with the Task 2 verify asserting a literal `"pdfkit": "0.20.2"` string in the manifest.
- **Actual:** installed as `^0.20.2` and `^0.17.7`, which is plain `pnpm add` default behaviour (no `--save-exact`, no hand-editing of the manifest).
- **Why:** the user asked that the dependency update itself. `.github/dependabot.yml` already covers the whole pnpm workspace weekly (npm ecosystem, directory `/`, production minor/patch grouped, majors separate), and that only tracks a package expressed as a range. An exact pin would have made pdfkit invisible to the group PR. Every other dependency in `apps/api` uses a caret; the exact `fflate: "0.8.2"` is a deliberate one-off for `healthIndex.ts` and was not copied as a style.
- **Verify adjusted:** the manifest-string assertion was replaced by an assertion on the lockfile resolution, which still reads exactly `0.20.2` and `0.17.7`. The plan's must-have truth "pdfkit 0.20.2 is the installed renderer" therefore holds today; the caret only governs future Dependabot bumps.
- **Cost if wrong:** a future Dependabot minor bump of pdfkit lands in a grouped PR and could change PDF output or break the font API without a plan revisit. Caught by the API test suite and the letter smoke tests that later plans in this phase add.
- **Files modified:** apps/api/package.json, pnpm-lock.yaml. **Commit:** ededbaf.

### 2. [Rule 3 - Blocking] Worktree dependencies were never installed

- **Found during:** Task 2, first `lint` run.
- **Issue:** `tsc --noEmit` failed with 30-plus `TS2307 Cannot find module 'drizzle-orm/mysql-core'` and `'zod'` errors from `packages/db` and `packages/shared`. Cause was environmental, not code: this worktree had no `node_modules` for any workspace other than `apps/api`, which my own `pnpm add` had just created.
- **Fix:** `pnpm install --frozen-lockfile` at the worktree root. It reported "Lockfile is up to date, resolution step is skipped" and added 219 packages across all 7 workspace projects. No manifest or lockfile content changed, and the frozen-lockfile pass is independent evidence that the lockfile my `add` produced is consistent with the manifests.
- **Cost if wrong:** none to the repo. If this had been misread as a real type error, the wrong fix would have been editing `packages/db` schema files, which are outside this plan's scope.
- **Files modified:** none (node_modules only). **Commit:** n/a.

### 3. [Startup] Worktree base correction

- The worktree was spawned at `5e4a52a`, one commit behind the plan base `010929e` (the commit that creates this phase's planning files), so the PLAN.md was not present. The prescribed startup assertion caught it and `git reset --hard 010929e` corrected it. The tree was clean beforehand, so nothing was discarded.
- **Cost if wrong:** had the reset run against a dirty tree it would have destroyed uncommitted work; `git status --short` was checked as empty first.

## Assumption Drift (advisory)

- **Assumption drift:** plan assumed exact version pins were the right expression of "pdfkit 0.20.2 is the installed renderer" -> the truth is now split across two files, the caret range in the manifest and the exact resolution in the lockfile (the user wants Dependabot to own future bumps). Later plans in this phase that want to assert the renderer version should read `pnpm-lock.yaml`, not `apps/api/package.json`. Cost if wrong: a later plan's verify command greps the manifest for a literal `0.20.2` and fails spuriously.
