## User Constraints (from CONTEXT.md)

### Locked Decisions

**Document rendering**
- **D-01:** The deliverable is a real PDF, A4 (210x297 mm), not an HTML print view and not text under a `.pdf` name. The letter ends up in a court file, so it has to be a fixed, paginated document.
- **D-02:** Render with a pure-JS PDF library added to `apps/api` (pdfkit is the default choice; pdf-lib is the fallback if font or layout work gets awkward). Do NOT render through Playwright/Chromium: `playwright` is already a dependency for `smovinScraper.ts`, but launching a browser inside the API process on the shared m1 box to make a letter is the wrong trade, and the Chromium binary is not guaranteed there.
- **D-03:** One shared renderer module (new, e.g. `apps/api/src/services/formalNotice.ts` plus a small `pdfDocument.ts` helper) used by both the formal notice and the final-reminder attachment.
- **D-04:** Fonts must render Dutch, French and German accents correctly. Verify a French and a German letter body before the plan is called done.
- **D-05:** `generateLatePaymentPdf()` in `apps/api/src/services/paymentFollowUp.ts:351` is replaced by the real renderer. Today it returns plain text with `contentType: "application/pdf"` and carries its own TODO: that attachment becomes a genuine PDF in this phase.

**Letter content**
- **D-06:** Fixed sections, in this order: sender block, addressee block, place and date, subject line naming it a formal notice of default, the contract reference (property address plus lease start date), the arrears table (period, due date, amount), interest and late fee lines where applicable, the total claimed, the payment instruction (IBAN plus the contract's structured communication), the payment deadline, the consequence paragraph, an optional free paragraph from the landlord, closing and signature block.
- **D-07:** The subject line and one sentence in the body state explicitly that the letter is a formal notice of default, so the document is self-identifying in a court file.
- **D-08:** The consequence paragraph states that if payment is not received by the deadline, dissolution of the lease and eviction will be sought before the justice of the peace, with interest and costs claimed. No threat the landlord cannot legally carry out (no lock changes, no re-letting, no self-help).
- **D-09:** The letter cites no statute article numbers. Belgian obligations law was recodified (Book 5 of the Civil Code, in force since 2023) and a wrong citation in a generated legal document is worse than none. The letter names the contract, the facts, the deadline and the consequence. Legal references stay out of the template.
- **D-10:** Payment deadline: default 15 calendar days from the letter date, overridable per generation in the request. Not a new settings field.
- **D-11:** One optional free-text paragraph the landlord can fill in before generating, inserted after the payment instruction. No full template editor in this phase.

**Address data**
- **D-12:** `users` gets a postal address (street, number, box, postal code, city, country default BE) for the sender block, editable in Settings. `tenants` gets an optional correspondence address with the same shape.
- **D-13:** The addressee defaults to the rented property's address from `properties` (street, streetNumber, postalCode, city, country already exist). The tenant's correspondence address overrides it when filled in, which is what makes the letter usable when the tenant has already left or sits elsewhere, including in prison.
- **D-14:** Generation fails with a clear, actionable error when the landlord's postal address is missing, naming the Settings page. Never generate a letter with a blank sender block.
- **D-15:** Schema change goes in with `db:push`, not `db:generate`. The 0000 Drizzle snapshot is stale and `db:generate` replays a non-additive backlog. Production needs the DDL applied in a human-run step, the same pattern as 11-07.

**Trigger, access and API**
- **D-16:** `POST /api/v1/payments/formal-notice` with `{ leaseId, deadlineDays?, extraParagraph? }`. Authorisation identical to `POST /api/v1/payments/send-reminder`: property access plus `manager` or higher, write scope for API-token callers, audit-logged.
- **D-17:** The response carries the PDF (or a short-lived download reference) plus the computed totals, so the UI can show what the letter claims before the landlord prints it.
- **D-18:** UI: a button in the arrears/reminder area of the contract detail page, next to the existing reminder actions. It opens a small dialog for deadline and the optional paragraph, then downloads the PDF.

**Logging and proof**
- **D-19:** Generating logs a row in `communications` with `channel: "letter"`, `direction: "outbound"`, a new `type` value `formal_notice`, `status: "queued"`, and metadata holding the deadline, the arrears breakdown and the total claimed. `body` holds the rendered letter text so the exact wording is reproducible.
- **D-20:** The landlord can mark the letter as posted: a date and an optional registered-item reference (bpost barcode). That sets `sentAt` and `status: "sent"`. This is the whole legal point of the feature, since the deadline runs from the posting date and the judge asks for that date.
- **D-21:** Adding `formal_notice` to the `communications.type` enum is a schema change, so it rides along with D-15.

**Arrears scope and money**
- **D-22:** The letter covers every outstanding month on the contract as of the letter date, not a single month. A formal notice that understates the debt forces a second one.
- **D-23:** Reuse the existing computation, add none: `loadContractBalance()` / `remainderRows` for what is open, `calculateInterest()` for interest, and the lease's `latePaymentFeeEnabled/Amount/Enforcement` for the fee. The amount in the letter must match the amount the final reminder would state.
- **D-24:** Interest and fee appear only when the contract provides for them. No default interest claim on a contract that does not carry one.

**Language**
- **D-25:** Letter body templates live in code as defaults per language, following the pattern of the reminder templates in `paymentFollowUp.ts`, selected by `tenants.language`. The landlord's own locale does not pick the letter language.
- **D-26:** Four languages are mandatory (NL, FR, DE, EN). New UI strings go in all four locale files; `apps/api/src/__tests__/i18n-completeness.test.ts` is the gate.

## Summary

This phase has almost no technical uncertainty left: every load-bearing claim below was verified by running real code in this session. The library choice is settled in pdfkit's favour on evidence stronger than the CONTEXT assumed, the font question has a clean answer, and the route, letter-text and arrears pieces all have close prior art in the repo that should be copied rather than reinvented.

**pdfkit 0.20.2 is the right choice and the bundling worry is obsolete.** pdfkit now ships a native ESM entry (`exports["."].node.import` -> `js/pdfkit.node.mjs`) and the standard-14 font metrics are compiled JS modules (`./standard-fonts/Helvetica.mjs`), not `.afm` data files read off disk. The classic "pdfkit + bundler = ENOENT Helvetica.afm" failure cannot happen here, and `tsup` keeps third-party deps external anyway. I built a replica of the project's exact tsup config (ESM, `platform: "node"`, the `createRequire` banner) against pdfkit and ran the output: it produced a valid PDF. Meanwhile pdf-lib's last release was **May 2022**, three and a half years stale, so the "fallback" in D-02 is a worse fallback than the CONTEXT assumed.

**Accents work out of the box, but non-Latin-1 names silently corrupt.** With the built-in Helvetica, NL/FR/DE accents (`é è ê ë à ç ô û ü ä ö ß œ`) and the euro sign all render and extract correctly: Helvetica uses WinAnsi/cp1252, which covers them. The trap is that anything **outside** cp1252 is not an error, it is garbage: `Łukasz Wójcik` came out as `V¶7¢Wójcik`, `Ștefan` as `!‡FV`an`, `Ayşegül` as `AyöV•ÆÂÂ\u20146Ö\u2013Â`, Cyrillic as mojibake. A tenant with a Polish, Romanian, Turkish, Czech or Cyrillic name would get a court document with a mangled addressee block. The fix is one line: `doc.registerFont("body", "<path>.ttf")`, which routes through fontkit and embeds a subsetted Identity-H font. I verified all of the above names render and extract correctly that way, with bold, in a column table, at 22 KB per letter. Ship Liberation Sans Regular + Bold (SIL OFL 1.1, 825 KB total) in the repo.

**Two latent defects sit on the path this phase has to touch.** First, the final-reminder PDF attachment is **already broken in production**: `generateLatePaymentPdf()` returns a `Buffer`, `queueEmail()` puts it in BullMQ, BullMQ JSON-serialises job data into Redis, and the worker hands the revived `{type:"Buffer",data:[...]}` object straight to nodemailer, which throws `The "chunk" argument must be of type string or an instance of Buffer`. I reproduced the throw and verified two fixes. D-05 therefore is not just "make the bytes real", it is "make the attachment actually arrive". Second, D-15's `db:push` instruction is contradicted by a recorded production fact: `drizzle-kit push` throws `TypeError: reading 'checkConstraint'` introspecting this MariaDB, and Phase 11-07 shipped by hand-reviewed DDL applied directly on m1. Hand-written idempotent DDL is the proven path, and it is the only path for an `ALTER TABLE ... MODIFY COLUMN` enum change.

**Primary recommendation:** Add `pdfkit` + `@types/pdfkit` to `apps/api`, commit Liberation Sans Regular/Bold TTFs under `apps/api/assets/fonts/`, and split the work into three pure-function layers (`pdfLetter.ts` layout primitives, `formalNoticeText.ts` per-language copy modelled on `indexationEmail.ts`, `formalNotice.ts` DB orchestrator), returning the PDF base64-encoded inside the existing JSON envelope rather than as a raw binary body.

### Pattern 1: Three pure layers, one impure orchestrator

**What:** Split the renderer so that only one of four modules needs a database.
**When to use:** Always, for this phase. It is what makes Nyquist validation cheap (see Validation Architecture) and it is exactly how `indexationEmail.ts` is already built.

- `lib/pdfLetter.ts` - takes a plain data structure, returns a `Buffer`. Knows pdfkit, knows nothing about leases.
- `services/formalNoticeText.ts` - takes a plain params object, returns `{ subject, body }` plus the structured sections. Knows four languages, knows nothing about pdfkit or the DB.
- `services/formalNotice.ts` - the only module that touches `getDb()`. Loads, computes, calls the two pure modules, logs the communication.
- `routes/payments.ts` - authorisation and HTTP only.

### Pattern 3: Authorisation by copy, not by re-derivation

**What:** The `/send-reminder` handler is the reference implementation. Write-scope enforcement and PAT audit logging are **not** in the handler, they are global middleware, so the new route inherits them for free.

### Pattern 4: Base64 PDF inside the existing JSON envelope

**What:** Return `c.json({ data: { pdfBase64, filename, totals, communicationId } })` instead of `c.body(pdfBuffer)`.

**Why this resolves D-17.** D-17 asks for the PDF *and* the computed totals in one response, which a raw binary body cannot carry. The options and their costs:

| Option | Cost |
|--------|------|
| **(a) JSON + base64 PDF + totals** (recommended) | +33% bytes on a ~22 KB document, i.e. ~30 KB. One round trip. No CORS change. Route test asserts on JSON. Client does `atob` -> `Uint8Array` -> `Blob`. |
| (b) Binary body + totals in custom headers | `apps/api` uses `cors({ origin, credentials: true })` with **no `exposeHeaders`**, so JS in the browser cannot read any custom header or `Content-Disposition` cross-origin. Would need a middleware change. |
| (c) Two endpoints: POST returns totals, GET returns bytes | Needs either stored bytes (new storage) or deterministic re-render. Nice later, unnecessary now. |

Note also that a plain `window.open(apiUrl + ...)` download is not viable: the endpoint is a POST, and `www.rentular.com` -> API is same-site but the app consistently uses `fetch(..., { credentials: "include" })`.

**For the record, raw binary does work** if a later phase wants option (c). Verified against the repo's own Hono:
```
status 200  ct application/pdf  cd attachment; filename="notice.pdf"  bytes 23
```
`c.body(buffer)` works (a Node `Buffer` is a `Uint8Array`), `prettyJSON()` ignores non-JSON content types, and the global no-store middleware only sets `Cache-Control` when absent. The blocker is purely the CORS `exposeHeaders` gap, not Hono.

**What:** The production schema step, modelled on `11-07-PLAN.md` Task 2 (`type="checkpoint:human-action" gate="blocking"`).

### Anti-Patterns to Avoid

- **Re-implementing euro/date formatting.** `apps/api/src/lib/belgianFormat.ts` already does `€ 1.150,00`, `dd/mm/yyyy`, `5 april 2019` / `1er avril 2019` / `5. April 2019`, country names and `65 bus 102`. Nine call sites already use it.
- **Putting letter copy in `apps/web/messages/*.json`.** Those are keyed on the *landlord's* locale via `next-intl`. D-25 keys on `tenants.language`. The letter copy belongs in `apps/api`.
- **Adding explicit `requireWriteScope` / audit calls in the new handler.** Already global. Duplicating them is noise and risks divergence.
- **Running `pnpm --filter @rentular/db db:generate`.** It replays a non-additive backlog (8 phantom `CREATE TABLE`, 20+ `ALTER TABLE`) because the `0000` snapshot is stale. Recorded in `drizzle-baseline-stale` memory and in `11-07-SUMMARY.md`.
- **Inserting `formal_notice` in the middle of the `communications.type` enum list.** Append it last, after `internal_note`. See Pitfall 4.
- **Making the arrears table from `remainderRows.ts`.** Despite D-23's wording, `remainderRows.ts` exports a *sweep job* (`sweepRemainderRows`) that writes `payments` rows; it returns `{inserted, updated, cancelled}`, not an arrears view. The per-month breakdown comes from `loadContractBalance(...).perMonth`. See Don't Hand-Roll.
- **Em-dashes or en-dashes anywhere in the templates.** Project rule. pdfkit renders them fine, which is exactly why a lint-style test is needed instead of relying on it failing loudly.

## Common Pitfalls

### Pitfall 1: Standard-font text silently corrupts non-Latin-1 names

**What goes wrong:** With the built-in Helvetica, any character outside WinAnsi/cp1252 renders as garbage. No exception, no warning.
**Reproduced in this session:**

| Input | Rendered (extracted with `pdftotext`) |
|-------|---------------------------------------|
| `Łukasz Wójcik` | `V¶7¢Wójcik` |
| `Ștefan Ionescu, Mihăiță` | `!‡FV`an Ionescu, Mih6’0` |
| `Ayşegül İsmail` | `AyöV•ÆÂÂ\u20146Ö\u2013Â0smail` |
| `Dvořák` | `Dvož°` |
| `Иванов` | `A„2C=Cä2` |
| `محمد` | `dV-dV/` |

**Why it happens:** the 14 standard PDF fonts are single-byte WinAnsi-encoded. cp1252 happens to cover the whole NL/FR/DE/EN accent set (`é è ê ë à â ç ô û ù ü ä ö ß œ ÿ É Ç Ü`) and `€`, so D-04's literal requirement is met by Helvetica and the bug stays invisible in testing. It surfaces on the first Polish, Romanian, Turkish, Czech, Hungarian or Cyrillic tenant name, which the Belgian rental market certainly has.
**How to avoid:** `doc.registerFont("body", fontPath)` with a committed TrueType file. Verified working: all six rows above render and extract correctly, `pdffonts` reports `CID TrueType / Identity-H / emb yes / sub yes / uni yes`.
**Warning signs:** any test fixture whose names are all ASCII or Western-European. Put `Łukasz Wójcik` and `Ayşegül` in the test fixtures deliberately.

### Pitfall 2: Combining diacritics (NFD) render as garbage even with an embedded font

**What goes wrong:** `"Angèle"` (NFD-decomposed) came out as `Ange0ÆP`.
**Why it happens:** the decomposed form needs a combining-mark glyph plus correct mark positioning. The precomposed `è` works everywhere.
**How to avoid:** `String.prototype.normalize("NFC")` on every string that reaches `doc.text()`. Do it once, centrally, inside `lib/pdfLetter.ts`, not at each call site. Database values from a web form can arrive NFD, especially from macOS clients.
**Warning signs:** a name that looks right in the UI and wrong in the PDF.

### Pitfall 3: `drizzle-kit push` does not work against the production MariaDB

**What goes wrong:** D-15 instructs `db:push`, but drizzle-kit 0.31.9 throws `TypeError: reading 'checkConstraint'` while introspecting this MariaDB. `db:generate` is worse: the stale `0000` snapshot makes it emit 8 phantom `CREATE TABLE` and 20+ `ALTER TABLE` statements against tables that already exist.
**Why it happens:** phases 2 through 9 maintained production with `db:push`, never committing migration files, so the snapshot drifted; and drizzle-kit's MariaDB introspection is broken at this version.
**How to avoid:** hand-written idempotent DDL, reviewed before it runs, applied by the operator with `mysqldump rentular` taken first. Charset `utf8mb4_unicode_ci` to match existing tables. This is what Phase 11-07 actually did (`11-07-SUMMARY.md`: "applied by extracting only the two-table statements ... and applying them directly"), and it is recorded in both the `drizzle-baseline-stale` and `deployment-m1-hetzner` memories.

### Pitfall 4: Enum value position matters

**What goes wrong:** MySQL/MariaDB store `ENUM` values as ordinal indexes. There is no `ADD VALUE IF NOT EXISTS`; the whole list must be restated in a `MODIFY COLUMN`. Inserting a value in the middle shifts every later ordinal and forces a full table rebuild.
**How to avoid:** append `'formal_notice'` as the **last** value. The column goes from 15 to 16 values, still within one storage byte (<= 255), so the change is cheap and non-destructive. Keep the Drizzle schema array order byte-identical to the DDL, or a future `db:push` will propose a reorder.
**Warning signs:** a diff that alphabetises the enum list.

### Pitfall 5: A `Buffer` attachment cannot survive the BullMQ queue (existing production bug)

**What goes wrong:** `generateLatePaymentPdf()` returns a `Buffer`; `queueEmail()` puts it in BullMQ job data; BullMQ JSON-serialises job data into Redis; `emailQueueWorker.ts:48-51` destructures `attachments` out of `job.data` and passes it straight to `sendEmail()`; nodemailer receives `{ type: "Buffer", data: [...] }`.
**Reproduced in this session against the repo's own nodemailer:**
```

JSON round-tripped  -> THREW: The "chunk" argument must be of type string or an
                       instance of Buffer, TypedArray, or DataView.
                       Received an instance of Object
```
**Consequence today:** every final reminder fails in the worker, BullMQ retries three times, and the email never arrives. The current plain-text content hides nothing: it is a `Buffer` too. This is a live defect on exactly the code path D-05 touches, and the phase must fix it or the "real PDF" change will look like a regression it did not cause.
**Two verified fixes** (both produce MIME output byte-identical to the real-`Buffer` case):
```ts
// (a) recommended: base64 string at the producer, nodemailer-native, queue-safe

  filename: "ingebrekestelling.pdf",
  content: pdfBuffer.toString("base64"),
  encoding: "base64",
  contentType: "application/pdf",

// requires widening EmailOptions.attachments in apps/api/src/lib/email.ts:55-59:
//   content: Buffer | string;  encoding?: "base64";

// (b) alternative: revive in the worker

```

**Warning signs:** `[EmailQueue]` errors mentioning "chunk" in production logs.

### Pitfall 6: `generateLatePaymentPdf()` must become `async`

**What goes wrong:** pdfkit is stream-based; the `Buffer` is only complete after the `"end"` event. The current function is synchronous.
**How to avoid:** make it `async` and `await` it. `sendPaymentReminder` is already `async`, so the call site change is one `await`. Keep the resolution pattern in one place:
```ts
const chunks: Buffer[] = [];
doc.on("data", (c: Buffer) => chunks.push(c));
const done = new Promise<void>((resolve) => doc.on("end", () => resolve()));
doc.end();
await done;
return Buffer.concat(chunks);
```
**Warning signs:** a zero-byte or truncated PDF. That means `doc.end()` was not awaited.

### Pitfall 7: Font path resolution differs between `tsx` (production) and the tsup bundle

**What goes wrong:** production runs `tsx src/index.ts`, so `import.meta.url` points inside `src/`. `pnpm build` emits a single `dist/index.mjs`, so `import.meta.url` points inside `dist/`. A single hardcoded relative path is wrong in one of the two, and **the one that breaks is whichever nobody tested**.
**Why it happens:** `pnpm --filter @rentular/api build` runs in CI/lint flow and must pass, but `deployment-m1-hetzner` records that the live API does **not** run the bundle. tsup bundles JavaScript only; it does not copy a `.ttf`.
**How to avoid:** a small resolver that tries candidates and throws a clear error naming the paths it tried, plus a unit test that it finds the file. Keep `process.cwd()` out of it: PM2's cwd is set per app and is not a contract.
```ts
// lib/pdfLetter.ts
import { existsSync } from "node:fs";
import { fileURLToPath } from "node:url";
import { join, dirname } from "node:path";

const CANDIDATES = ["../../assets/fonts", "../assets/fonts", "./assets/fonts"];

function fontDir(): string {
  const here = dirname(fileURLToPath(import.meta.url));
  const fromEnv = process.env.FORMAL_NOTICE_FONT_DIR;
  const tried: string[] = [];
  for (const rel of fromEnv ? [fromEnv, ...CANDIDATES] : CANDIDATES) {
    const dir = rel.startsWith("/") ? rel : join(here, rel);
    tried.push(dir);
    if (existsSync(join(dir, "LiberationSans-Regular.ttf"))) return dir;
  }
  throw new Error(`[FormalNotice] letter font not found. Tried: ${tried.join(", ")}`);
}
```
**Warning signs:** the PDF renders locally and the API throws `ENOENT` only in production.

### Pitfall 8: `markCommunication()` cannot record a backdated posting date

**What goes wrong:** D-20 needs `sentAt` set to the **posting** date, which the landlord enters after walking to the post office, possibly days later. `markCommunication(id, { status: "sent" })` hardcodes `sentAt: new Date()`.
**How to avoid:** a new update path, not a change to `markCommunication` (which eleven send paths depend on). `communications.externalId varchar(255)` already exists and is the right home for the bpost barcode, so **no schema change is needed for D-20**. Add `POST /api/v1/communications/:id/posted` with `{ postedOn: "YYYY-MM-DD", reference?: string }`, and copy the ownership check from `POST /:id/resend` (`communications.ts:149-168`), which already handles "owned by me OR linked to a lease on a property I manage" plus `hasMinimumRole(role, "manager")`.
**Also note:** `/:id/resend` refuses anything whose status is not `failed`/`bounced`. The new route needs its own guard, e.g. refuse when status is already `sent`, or allow a correction. Decide explicitly.
**Warning signs:** a plan task that edits `markCommunication`.

### Pitfall 9: The communications list page labels any non-email channel as SMS

**What goes wrong:** `apps/web/app/(dashboard)/communications/page.tsx:304-315` is a two-branch ternary: `channel === "email"` renders the Mail badge, **everything else** renders the `MessageSquare` + `channelSms` badge. A `letter` row will read "SMS". (`whatsapp` and `signal` rows already do.)
**How to avoid:** replace the ternary with a channel map, and add `communications.channelLetter` (and ideally `channelWhatsapp` / `channelSignal`) to all four locale files. ### Pitfall 10: The letter total and "what the final reminder would state" are not the same number

**What goes wrong:** D-23 requires both "every outstanding month" (D-22) and "the amount in the letter must match the amount the final reminder would state". A reminder claims **one month**, capped at the whole-contract `owed`:
```ts
// manualReminder.ts:159-166 (verified in repo)
const capped = cappedReminderAmount(amount, balance.owed);  // min(monthAmount, owed)
```
So a final reminder for September on a contract three months in arrears states roughly one month's rent, while the letter states three. The two numbers cannot both be right.
**How to avoid:** read D-23 as "derive from the same functions, never a parallel computation". Concretely:
- per-month row amount = that month's `shortfall` from `perMonth`,
- authoritative total rent claimed = `balance.owed`,
- if `sum(shortfalls) !== balance.owed`, show `balance.owed` as the total and reconcile the difference explicitly rather than silently.
**Why they can differ:** `contractBalance()` computes `received` across the whole contract and subtracts `arrearsRepaid` and `paidInAdvance` globally, while `perMonth[].received` uses per-month attribution (`receivedForMonth`). A tenant who overpaid one month and underpaid another produces a legitimate mismatch.
**This needs a user decision. See Open Question 1.** It is the one substantive modelling question in the phase, and a letter that overstates the debt is worse for the landlord in front of a judge than one that understates it.

### Pitfall 11: Interest is a per-owner setting but D-24 is framed per contract

**What goes wrong:** D-24 says interest appears "only when the contract provides for them", but `interestEnabled` and `annualInterestRate` live on `payment_follow_up_settings`, keyed `ownerId` (unique). The late **fee** is genuinely per lease (`leases.latePaymentFee*`); interest is not.
**How to avoid:** do not add a per-lease interest column (out of scope, and it would fork the reminder path). Treat the owner-level `interestEnabled` as the gate, and say so in the plan so the discrepancy is a recorded decision rather than a silent one. See Open Question 2.

### Pitfall 12: Interest over multiple months needs per-month `daysPastDue`

**What goes wrong:** `calculateInterest(amount, daysPastDue, rate)` takes a single age. Calling it once with the total and the oldest month's age overstates interest; calling it with the newest month's age understates it.
**How to avoid:** one call per arrears month, with `daysPastDue` computed from that month's own `dueDate` (available as `perMonth[].dueDate`) against the letter date in the resolved timezone, then sum and round once. Put the loop in the pure text/calc module so it is unit-testable without a DB.

## Open Questions (RESOLVED)

All five are closed as recorded below, by the decisions in `11.2-CONTEXT.md` plus one accepted risk. Nothing here is still waiting on an answer before execution.

### 1. What total does the letter claim when the per-month shortfalls do not sum to `balance.owed`?

**RESOLVED by D-32:** the recommendation was taken. The claimed rent is `loadContractBalance(...).owed`, the per-month table is the breakdown, and when the two differ by more than half a cent one labelled line reconciles them. Plan 11.2-03 carries the arithmetic and plan 11.2-05 carries `balance.owed` as the claimed figure.

- **What we know:** `perMonth[].shortfall` is per-month attribution; `balance.owed` is `expected - received` over the whole contract with `arrearsRepaid` and `paidInAdvance` netted out globally. They normally agree. They diverge when a tenant overpaid one month and underpaid another, when money was marked as repaying pre-tracking arrears, or when rent is paid in advance for a month not yet due.
- **What's unclear:** whether the letter should claim `sum(shortfalls)` (matches the table, may overstate) or `balance.owed` (matches what the app says is owed everywhere else, may not equal the table).
- **Recommendation:** claim `balance.owed` as the authoritative rent figure, show the per-month table as the breakdown, and when `sum(shortfalls) - balance.owed > 0.005`, add one sentence crediting the difference ("already received and credited: € X"). Overstating a debt to a judge is the worse failure. The service should return both numbers so the UI dialog can show them before printing, per D-17.

### 2. Interest is per owner, not per lease. Is that what D-24 means?

**RESOLVED by D-33:** use the owner-level flag for this phase, no new per-lease column, and record the discrepancy. A per-lease interest flag is a separate item, listed under Deferred Ideas in CONTEXT.md.

- **What we know:** `payment_follow_up_settings.interestEnabled` / `.annualInterestRate` are keyed on a unique `ownerId`. `leases.latePaymentFee*` is genuinely per contract.
- **What's unclear:** D-24 says "only when the contract provides for them". A landlord whose global setting has interest on would get an interest claim on a contract whose lease text does not provide for it.
- **Recommendation:** use the owner-level flag for this phase (no new column, no fork of the reminder path), and surface the interest line in the generate dialog so the landlord can see it before printing. If a per-lease interest flag is wanted, defer it as its own item. Record whichever the user picks as a decision.

### 3. Does Belgian Book XIX WER reach a landlord, and is 15 days enough?

**RESOLVED as an accepted risk, partly by D-34.** The deadline default moves from 15 to 16 calendar days counted from the letter date, overridable per generation between 1 and 90 days. No statute citation enters the letter (D-09 stands).

The residual risk is stated plainly rather than papered over: if a landlord does count as an undertaking under Book XIX, a 16-day deadline counted from the letter date can land a day or two inside the 14-day waiting period, since that period starts on the third working day after postal dispatch. What is at stake in that case is the recoverability of the interest and the late fee, not the rent itself and not the validity of the notice. Three things make the risk tolerable: the principal is unaffected, the generate dialog shows interest and fee as separate lines so the landlord sees exactly what is being claimed, and the deadline is overridable, so a landlord who is an undertaking can set 21 days.

Deferred, not silently absorbed into this phase: a per-generation toggle to drop interest and fee, and a Book XIX determination per landlord type. Both are in CONTEXT.md under Deferred Ideas.

- **What we know, with sources:** the Act of 4 May 2023 inserted Book XIX ("Consumer Debts") into the Code of Economic Law, in force 1 September 2023 (1 December 2023 for contracts signed before that date). It requires a **free first reminder** before any penalty clause can be applied, and a **waiting period of at least 14 calendar days** before costs, interest or compensation may run. For postal reminders the period starts on the **third working day after dispatch**. Non-compliance can forfeit the right to recover the extra charges. SMEs may let interest run from the day after the first reminder.
- **What's unclear:** whether a landlord counts as an "undertaking" (entreprise/onderneming) for these purposes. A professional property manager or a company landlord plausibly does; a private individual letting one apartment plausibly does not. Searches did not resolve it, and the question is genuinely contested rather than merely undocumented. **LOW confidence.**
- **Why it matters here even though D-09 forbids citations:** three mechanical consequences, none of which require a statute reference in the letter. (a) The postal start rule means a 15-day deadline counted from the **letter date** can be under 14 days from the legally relevant start, so the deadline should be counted from the **posting date** (which D-20 already captures) or set to 15 days with the sentence "from receipt of this letter". (b) If the landlord is in scope and this is the *first* reminder, charging interest and a fee on it may be unrecoverable, so the generate dialog should show them separately and let the landlord drop them. (c) Book XIX also prescribes mandatory content for the reminder, and D-06's section list already covers all of it (outstanding balance, the charges claimed, the deadline, the creditor's identity and address) which is reassuring rather than actionable.
- **Recommendation (superseded by the RESOLVED line above; kept as history):** ask the user. Do **not** add any statute citation (D-09). Do make the deadline sentence reference receipt or posting rather than the letter date, and keep interest and fee individually visible and suppressible in the dialog. Suggest raising the D-10 default from 15 to 16 days so the arithmetic is comfortable regardless of how the waiting period is counted.

### 4. Co-tenants: one letter or one letter each?

**RESOLVED by D-35, against this section's recommendation.** One individually addressed letter per liable tenant, always, each rendered as its own PDF and each logged as its own `communications` row. The single-item variant proposed here (one PDF naming every co-tenant when they share an address) was considered and rejected: a formal notice puts its addressee in default, and one registered item is delivered to one person, so per-debtor dispatch proof is what a dispute would turn on. The cost is one extra registered item per co-tenant.

If that postage matters, the shared-address single-item variant is a cheap follow-on, since the service already returns a list.

- **What we know:** co-tenants are normally jointly liable for the whole rent, and the CONTEXT's own code-insights section flags that "a notice to one is not a notice to all". `getLeaseEmailRecipients()` returns every linked tenant. D-13 defaults the addressee to the property address, which all co-tenants share unless one has a correspondence address.
- **What's unclear:** CONTEXT does not decide. D-19 logs one communication row; D-20 records one posting reference.
- **Recommendation:** one PDF listing every co-tenant's name in the addressee block when they share an address (normal Belgian practice, one registered item, one barcode), and one PDF per co-tenant who has their own correspondence address (the prison case). The latter means the response may need to carry more than one PDF, and D-19/D-20 would need one communication row per letter. **This changes the response shape, so it must be settled before planning.**

### 5. Should the generated PDF be re-downloadable later?

**RESOLVED as out of scope, confirmed.** Not in this phase. Recorded in CONTEXT.md under Deferred Ideas as a one-task follow-on: a `GET` route that re-renders from the stored `body` and `metadata`. No byte storage is added now.

- **What we know:** D-19 stores the rendered letter text in `communications.body`, so the exact wording is reproducible. Bytes are not stored.
- **What's unclear:** whether the landlord needs to re-print months later when the case reaches the justice of the peace, which is precisely when they would.
- **Recommendation:** out of scope for this phase, but note it in the SUMMARY as a one-task follow-on: a `GET /communications/:id/formal-notice.pdf` that re-renders from the stored `body` and `metadata`. The three-layer split makes that cheap later. Do not add storage now.

### What `i18n-completeness.test.ts` actually asserts

Read it before planning locale work. Three suites, and the third is broader than its name suggests:

1. every locale has at least one `communications.*` key;
2. the `communications.*` key sets are **exactly equal** across `en`/`nl`/`fr`/`de` (it asserts both `missingInLocale` and `extraInLocale` are `[]`, so a key added to `nl` alone fails just as hard as one missing from `nl`);
3. **every key present in `en` exists in `nl`, `fr` and `de`** - the whole flattened file, not just `communications`. There is no reverse check outside the `communications` and `bankConnections` namespaces, so extra keys elsewhere are tolerated, but a missing one is not.

It reads `join(process.cwd(), "../web/messages", locale, "common.json")`, so it only works when run via `pnpm --filter=@rentular/api`. Consequence for the plan: adding `communications.typeFormalNotice`, `communications.channelLetter`, `contractComms.kind.formal_notice` and the new dialog/settings strings to `en` alone will fail the suite. All four files, same keys, same commit.

## Security Domain

`security_enforcement` is not set to `false`, so this section applies.

### Applicable ASVS categories

| ASVS Category | Applies | Standard Control |
|---------------|---------|-----------------|

### Known threat patterns

| Pattern | STRIDE | Standard Mitigation |
|---------|--------|---------------------|
| Cross-landlord IDOR: generating a notice for someone else's lease | Information Disclosure / Elevation | Copy the `/send-reminder` chain verbatim: lease -> `getAccessiblePropertyIds` -> `getUserPropertyRole` -> `hasMinimumRole("manager")`. Direct precedent: the fixed `bankAccounts.ts /:id` IDOR. |
| Cross-landlord IDOR on mark-as-posted | Information Disclosure / Tampering | Copy the ownership check from `communications.ts /:id/resend`: owner match **or** an accessible lease with manager+. Never authorise on `ownerId` alone, and never on the id alone. |
| A read-scoped PAT generating letters | Elevation of Privilege | `requireWriteScope` already applies to `/payments` and `/communications` as global middleware. Add a route test proving a read-scoped PAT gets 403. |
| Path traversal via a font or filename parameter | Tampering | No user input in any path. Fixed candidate list; filename composed server-side. |
| Content injection into the PDF via `extraParagraph` (D-11) | Tampering | pdfkit draws text, it does not execute it, so there is no script surface. Still cap the length, strip control characters other than newline, and cap newlines so a 2000-char paragraph of `\n` cannot blow the document to many pages. |
| Unbounded PDF generation as a resource exhaustion vector | Denial of Service | Each call runs `loadContractBalance` plus a render. `bearerRateLimit` covers PATs (120/min default) but **not** cookie sessions. Accept for now (consistent with every other write endpoint) and record it; the `max(90)` deadline bound and the paragraph cap keep per-call cost flat. |
| PII leakage through the audit log | Information Disclosure | `bearerAuditLog` stores the request body via `redactAuditArgs`. `extraParagraph` is **not** matched by its `token\|secret\|password\|iban\|authorization` pattern, so a landlord's free-text paragraph lands in `api_tool_calls.args` (truncated at 2000 chars) for PAT-authenticated calls. Low severity (same-owner data in the same database), but worth a one-line note in the threat register rather than discovering it in a later audit. |
| Logging the letter body to stdout | Information Disclosure | Log the communication id and the lease id, never the body. |
| Supply-chain compromise of a newly added package | Tampering | `checkpoint:human-verify` before `pnpm add` (slopcheck unavailable); pdfkit has no postinstall script; lockfile committed. |
| Destructive DDL against a shared production database | Tampering / DoS | `mysqldump rentular` first; additive `ADD COLUMN IF NOT EXISTS` only; the enum `MODIFY` restates the full list with the new value appended; operator reviews the exact statements; blocking human checkpoint. The box hosts ~40 unrelated databases, so scope every statement to `rentular`. |
