# Phase 11.2 Plan 06: Recording the posting of a letter Summary

**POST /api/v1/communications/:id/posted writes the day a registered formal notice was handed in at the post office, with the bpost barcode, under the same manager-or-higher rule as resend, and the contract history reads both back as postedOn and postedReference.**

## Accomplishments

- The feature's legal anchor is now recordable. `sentAt` becomes the submitted calendar day at noon UTC, not the moment of the request, so a landlord entering Friday's trip to the post office on the following Tuesday gets Friday stored. The test pins `2026-11-20T12:00:00.000Z` for a request made on a mocked "today" of 2026-11-24.
- Noon UTC is the chosen instant because the calendar day then reads the same in UTC and in Europe/Brussels. A midnight value would show as the previous day in Brussels for half the year.
- The ownership rule is the one from `POST /:id/resend`, copied without loosening: a lease-linked row requires `getUserPropertyRole` plus `hasMinimumRole(role, "manager")` on that lease's property, a lease-less row requires `ownerId === userId`. Authorisation never runs on the id alone, and never on `ownerId` alone when a lease is linked.
- A correction keeps the earlier record. Marking an already-posted letter appends the previous `{ postedOn, reference }` to `metadata.postedHistory` and stamps `postedBy` and `postedAt`, so an overwritten posting date is still visible in the row.
- Implausible dates are refused rather than stored: a day after today in the schedule timezone, a day before the letter row existed, and a string like `2026-02-30` that Node happily parses into 2 March. The ISO round-trip comparison is what catches that last one; `new Date("2026-02-30T12:00:00Z")` is **not** an Invalid Date in V8, it is March 2nd, which was verified at the node prompt before the check was written.
- Only letters can be marked. An e-mail or SMS row is a 400 with code `not_a_letter`, so nobody can give a queued e-mail a chosen send date.
- `markCommunication()` and its eleven callers are untouched, which was the explicit warning sign in research Pitfall 8.
- The contract history exposes `postedOn` and `postedReference` for letter rows only. On an e-mail row `externalId` is a queue job id, and a job id must never be readable as proof that something was posted; a test pins that to null.

## Decisions Made

- **Noon UTC for the backdated instant.** The plan specified it and the reason is worth keeping: with `T12:00:00Z` the calendar day of `sentAt` is the same whether it is read in UTC or in Europe/Brussels, so the day that shows in the history is the day the landlord typed.
- **`not_markable` as the status guard's error code.** Pitfall 8 asked for an explicit status decision and the plan's action text allows only `queued` and `sent`. Enforcing that needed a response, and the plan named no code for it, so `{ error: "This letter cannot be marked as posted", code: "not_markable" }` was chosen in the style of the two codes the plan does name. A test documents it.
- **`postedHistory` only when there is history.** The key is absent on a first posting rather than present as an empty array, so an untouched row does not grow a key that means nothing.
- **A comment in `communications.ts` names `markCommunication()`.** It explains why the update is inline, which is exactly the trap research flagged. A grep for the identifier in this file therefore returns one hit; it is prose, not a call.
- **The reference is trimmed and empty becomes null.** `reference: "  "` stores `null` rather than a blank barcode that would read as a reference that exists.

## Assumption Drift (advisory)

Nothing material drifted. The two interface claims this plan leaned on were accurate as described: `/:id/resend` at lines 149-168 holds exactly the ownership check that was copied, and `communications.externalId` is a free `varchar(255)` on letter rows, so the research conclusion that D-20 needs no schema change held up. The `manualMarks.test.ts` harness shape transferred without modification, including the chain-proxy caveat that plan 02 recorded: the proxy here is parameterised by statement kind, so `await db.update(...)` does not eat a queued select row.

One small thing worth recording for a later reader rather than as drift: the plan's phrasing "the update sets ... sentAt equal to 2026-11-20T12:00:00.000Z" is asserted on a `Date` object, not a string. Drizzle takes a `Date` for a timestamp column, so the test compares `(set.sentAt as Date).toISOString()`.

## Issues Encountered

- `new Date("2026-02-30T12:00:00Z")` is 2 March 2026, not an Invalid Date, so an `isNaN` check alone would have accepted a non-existent calendar day. This was checked at the node prompt before the validation was written, and the ISO round-trip comparison is what rejects it. The test for `2026-02-30` would have passed anyway (it lands after today), which is precisely why the round trip is asserted by its own code path rather than trusted.
- The mocked `../../lib/timezone` must export every member the real module has, because `routeAuth` and other importers pull from the same graph. The mock returns a fixed `todayInZone` of `2026-11-24` and a real UTC slice for `ymdInZone`, which keeps the backdating assertion honest instead of relative to the clock the suite happens to run on.
