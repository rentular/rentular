# Phase 11.2 Plan 05: Formal Notice Orchestrator and Endpoint Summary

The database half of the formal notice: `generateFormalNotice` loads the contract and renders one individually addressed, logged PDF per liable tenant, and `POST /api/v1/payments/formal-notice` returns those letters as base64 with the totals behind the same authorisation as the manual reminder.

## What was built

**apps/api/src/services/formalNotice.ts** (new, 14.6 KB)

Six selects in a fixed order: lease, property, landlord (`users`), liable tenants (`lease_tenants` inner join `tenants`, primary first then by last name), bank account, owner follow-up settings. Then:

- Sender block from `users`, with `bank_accounts.holder_name` as the name fallback. Missing name, street, postal code or city refuses with `missing_sender_address` and an error naming Settings (D-14). Nothing is rendered and nothing is logged.
- `loadContractBalance(db, lease, todayInZone(getScheduleTimezone()))` decides what is open. `balance.owed` is the rent claimed, `balance.perMonth` filtered on not settled, not ignored and shortfall above zero is the table, oldest first (D-22, D-32). No SQL against `payments`, no `remainderRows`, no `cappedReminderAmount`.
- `computeFormalNoticeTotals` with `calculateInterest` from `paymentFollowUp`, the owner-level interest flag and the lease's late-payment fee (D-23, D-33). Interest source recorded as `owner_setting` in the metadata.
- Per tenant: addressee is the correspondence address when street, postal code and city are all filled, else the rented property (D-13); letter built in that tenant's own language (D-25); rendered through `renderLetterPdf`; logged via `logCommunication` with channel `letter`, type `formal_notice`, the rendered text as body and the whole claim in metadata (D-19).
- Filename is `ingebrekestelling-{leaseId}-{letterDate}-{n}.pdf`, composed from the lease id, the server date and a counter only (T-11.2-22).
- One stdout line: `[FormalNotice] generated N letter(s) for lease <id>`. No body, no name, no address (T-11.2-23).

**POST /api/v1/payments/formal-notice** (apps/api/src/routes/payments.ts, directly after `/send-reminder` per D-16)

Zod: `leaseId` 1 to 64 characters, `deadlineDays` integer 1 to 90 optional, `extraParagraph` up to 2000 characters optional. Then the send-reminder chain verbatim: lease lookup (404), `getAccessiblePropertyIds` (403), `getUserPropertyRole` plus `hasMinimumRole(role, "manager")` (403). Only then is the service called, with `trigger: api` for a token call and `manual` for a session. `ok: false` becomes a 400 carrying `{ error, code }`; the happy path returns `{ data: { letters, totals: { ...totals, currency: "EUR" }, arrears, letterDate, deadline, deadlineDays } }` (D-17 as corrected by D-31 and D-35). A thrown error logs with the `[Payments]` prefix and answers a generic 500.

No `requireWriteScope`, `requireAuth` or audit call inside the handler: all three are global middleware for `/payments`.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 2 - Missing critical behaviour] Spy-wrapped the real PDF renderer instead of leaving it unobservable**
- **Found during:** Task 1
- **Issue:** The plan says not to mock `lib/pdfLetter` (so the tests render real PDFs) while also requiring the assertion that `renderLetterPdf` is not called on a refusal. A plain ESM import gives no call counter, so that acceptance criterion was unverifiable as written.
- **Fix:** `vi.mock("../../lib/pdfLetter", async (importOriginal) => ...)` keeps the real `renderLetterPdf` and routes every call through a spy first. Real pdfkit output is still asserted (decoded base64 starts with `%PDF`), and refusals now provably draw nothing.
- **Cost if wrong:** A refusal path could start rendering letters it should not and the test would stay green; cost is one weaker assertion, no product behaviour.
- **Files modified:** apps/api/src/services/__tests__/formalNotice.test.ts
- **Commit:** 60d8e86

**2. [Rule 3 - Blocking] Error sentences invented for three refusal codes**
- **Found during:** Task 1
- **Issue:** The plan specifies the exact error text for `missing_sender_address` and `nothing_owed` only, but `lease_not_found`, `no_tenant` and `missing_bank_account` also return an `error` string by the declared result type.
- **Fix:** Added module constants: `"Lease not found"` (matching the route's own 404 wording), `"This contract has no tenant to address the letter to"` and `"This contract has no bank account, so the letter cannot name where to pay"`. The UI translates on `code`, so these are fallback text.
- **Cost if wrong:** Untranslated English fallback text appears in a UI that should key off the code; no data or authorisation impact.
- **Files modified:** apps/api/src/services/formalNotice.ts
- **Commit:** a2470df

**3. [Rule 1 - Correctness] A lease whose property row is gone refuses rather than crashing**
- **Found during:** Task 1
- **Issue:** `properties` is read by id from `lease.propertyId`; the plan has no code for a lease pointing at a deleted property, and the addressee builder would have dereferenced undefined.
- **Fix:** A missing property row returns `lease_not_found` (the lease is unusable), placed after the sender check so the read order the test pins is unchanged.
- **Cost if wrong:** A data-integrity case gets a slightly misleading code instead of a 500; it should not occur, since `leases.property_id` is a foreign key.
- **Files modified:** apps/api/src/services/formalNotice.ts
- **Commit:** a2470df
